# RG Houdini Bridge: parameters

How the Houdini parameters become inputs of the modifier, and the code parameters. Part of the developer documentation: start with [DEVELOPMENT.md](../../DEVELOPMENT.md).

- [Parameters](#parameters)
- [Code parameters](#code-parameters)

## Parameters

`blender/core/parameters/` turns the Houdini parameters into inputs of the modifier's node group, and `houdini/parms.py` describes them and writes the values Blender sends.

- **Registries**:
  - what depends on the kind of a parameter (`contract.PARM_KINDS`) is written once on each side. On the server, `houdini/parms.py` has one handler per kind in `KINDS`: `describe` adds the fields of its kind to a description that holds the common ones, `write` sets a value.
  - Which kind a template is described as is one decision for every template, so it stays one function, `kind_of(template, menu)`, where the order of the tests matters (a String template with a `StringReplace` or `StringToggle` menu is a `string` with suggestions, any other template with a one-component menu is a `menu`, an Int one included, the others follow their template type through `TEMPLATE_KINDS`).
  - Writing does not evaluate menus: `written_as(template)` finds the handler from the template type alone, so a menu on an Int template is written by the `int` handler, which takes a token, and a template no kind writes (the count of a multiparm is a folder) goes to `set_components`.
  - On the Blender side, `parameters/kinds.py` has `KINDS`, one `Kind` per kind: a record of functions with no state, since a parameter's state is its `HoudiniBridgeParm`.
  - A `Kind` holds what several kinds do, each its own way: its socket type, how it enters the usage chain (a Menu Switch, a String Length, or stored as it is), how it reads and converts values, whether it has a range, what it copies from a description and what in its description rebuilds the inputs (`signature`).
  - What one kind alone does is a plain function, called where it is needed after a test of `contract.RAMP` or `contract.STRING`: the node holding a ramp (`ramps.py`: its name, made by `sync_interface`, read and written by `read_value` and `write_value`, its `ramp_basis` kept over a rebuild by `apply_description`), what a string takes from every answer (`refresh_from_answer`), the values a group field offers and how one is picked (`group_suggestions`, `pick_group`, `group_selection`); and consecutive buttons share a row (`parameters/layout.py`).
  - How a kind draws its row in the modifier panel (its input, a group field's picker and arrow, a ramp's widget, a button, a multiparm count with + and -) is the interface's: `ROWS` of `ui/parameter_rows.py`, one `Row` per kind.
  - `tests/unit/test_parm_registry.py` checks that the three registries (`KINDS` on each side and `ROWS`) hold the names of `contract.PARM_KINDS`, in that order, that each field the server writes is declared for its kind in `contract.PARM_FIELDS`, and that no code names a kind by its string rather than its contract constant.
- **Multiparms are no kind** but a structure of the walk: `describe_parms` gives the count as an `int` with `multiparm: true`, then the instances as folders, and `set_parms` sets values in passes. They stay in the walk of the templates on the server and in the signature on the Blender side.
- **Sockets by kind**: Float, Vector (2 to 4 dimensions), Color, Int, Bool, String, Menu. Folders become panels of the node group's interface (what Blender draws with the Houdini interface off). Buttons and ramps are not inputs.
- **Who draws them: the Houdini interface.**
  - `ui/modifier_panel.py` is a child panel of `MOD_PT_GeometryNodes`, drawn under every Geometry Nodes modifier, which draws nothing for one that is not Houdini's (`context.modifier` is None there, so `poll` cannot tell; the panel reads `custom_data`, the modifier).
  - For Blender not to draw the inputs too, `parameters.apply_houdini_interface` hides every input from Blender's drawing (`hide_in_modifier`) and each modifier's node group selector and Manage panel (`show_group_selector`, `show_manage_panel`); `apply_houdini_interface(tree, False)` turns it off (an input hidden when `is_hidden`, the selector and Manage shown).
  - It is applied at a modifier's creation, at each cook (`apply_description`), when a file is loaded (`cook/handlers.on_file_loaded`, a file saved before 1.0 included), after a registration (a timer, `modifier_panel.apply_houdini_interface_after_register`: Blender registers an extension with its data out of reach) and when the preference *Houdini Interface* changes; turned off when that preference is off and in `unregister()`, so that a disabled extension leaves no empty modifier.
  - Only what differs is written: a change of the interface makes the depsgraph evaluate the modifier again, which reads input 1 once and sends nothing. A file saved with the Houdini interface on shows empty modifiers in a Blender without the extension: the preference off is the way to share one. Nothing turns it off before a save: it would evaluate every Houdini modifier again and leave the file marked modified.
- **What the panel draws**:
  - the core lays the parameters out as data (`parameters/layout.py`), and the interface draws them (`ui/parameter_rows.py`).
  - A plan per node group, made once per structure (`plan`, `forget_layout` when a cook brings other folder types, and on load and undo), turns `settings.parms`, in Houdini's order, into nested folders from each parameter's folder path and `folder_types`, each folder told apart from its siblings by its Houdini name (its `key`), and shown by its label (its `path`).
  - The painter (`parameter_rows.Painter`) draws a collapsible folder as a `UILayout.panel` (its id, `parameters.panel_id`, holds the node group's name and the folder's key: Blender keeps the open state in the panel instance, which the Properties editor reuses for the modifier at the same place of another object), a simple folder as a box with its title (none for an unlabelled one), a set of tabs as a row of tab buttons (`houdini_bridge.folder_tab`, rows wrapped to the region's width at the UI scale) over the open tab's content, a multiparm instance as a box.
  - Each draw walks the plan (`parameters.walk`), leaves out what `is_hidden` hides, kinds this version does not know and folders with nothing to show, and draws each parameter's row (`ROWS`); a parameter Houdini disables (`disabled`, as the last cook found it) is drawn faded (`UILayout.active` false), not locked, since the state may be older than the values.
  - The open tab of each set lives in memory only (`set_open_tab`), by its Houdini name: changing tabs writes nothing, so it cooks nothing and reads no input; a file loaded forgets them. `parameters.drawn` lists what the panel would draw, for the tests.
- **Folder types** (`folder_types`):
  - the server gives one `[type, tab set, name]` per level of a parameter's folder path (`houdini/parms.py`, `FOLDER_TYPES`): Collapsible, Simple (and an import block: simple), Tabs and RadioButtons (tab), a multiparm instance (instance). Adjacent tab folders form one set, named after its first folder (the name of the set's folder-set parameter), unless one ends its set (`endsTabGroup`).
  - The name is the folder's Houdini name, unique in the node (an instance: its count's name and number), so two sibling folders of one label (unlabelled Simple folders used as separators, two "Settings") stay two, in Houdini's order. Blender stores it in `HoudiniBridgeParm.folder_types` at every cook, without a rebuild: the node group's interface does not depend on it.
  - A file saved before 1.0 may have none before its first cook: its folders are collapsible. A file saved before 1.0 may have levels of two items: its folders are told apart by their labels until its next cook, which brings the names and makes the plan again (the collapsible folders open then start folded once).
- **Menus**: a Menu Switch node defines the items (the Houdini labels, made unique), and the value maps back to the Houdini token.
- **Usage chain**: Blender greys out group inputs that do not reach the output. Each input is therefore stored by a Store Named Attribute node on the Instance domain, chained between Object Info and Group Output. A mesh has no instances, so nothing is stored, but `is_input_used` is true.
- **Reading and writing**: Blender 5.2 reads and writes modifier inputs through `modifier.properties.inputs.<identifier>.value` (`parameters.modifier_input`), with menus as item names. A Geometry Nodes modifier has no ID properties in Blender 5.2, the minimum version of the extension.
- **Change detection**: changing a modifier input fires no depsgraph update a handler sees. `cook/scheduler.poll_modifier_inputs` compares the values with the last ones sent, ten times a second. This also covers keyframes and drivers.
- **Limits**:
  - Houdini has a slider range, which values may leave, and strict bounds (`minIsStrict`, `maxIsStrict`). Blender inputs have only hard limits (`min_value`, `max_value`, none on colors). On SideFX Labs, of 4,046 numeric parameters, 1,118 have a strict minimum and 1,967 have a non-strict range starting at 0 (offsets and spacings may be negative), so slider ranges cannot all become limits.
  - The *Limits* preference chooses `STRICT`, `MINIMUM` (default: strict bounds and the slider minimum) or `RANGE`. A parameter keeps its whole range (`store_range`), and `parameters.limits` decides from the preference. A default outside the range means the range is no limit for it.
  - Nothing in Blender 5.2 enforces these limits on modifier inputs (a script writes -5 and it stays), so `parameters.hold_within_limits` puts an input back from the 10 Hz poll, and `read_value` bounds every value sent.
- **Ramps**:
  - a Float Curve or Color Ramp node of the node group holds the value (`Ramp · <parm>`, kept across rebuilds), drawn at its place in the modifier panel with `template_curve_mapping` and `template_color_ramp`. The 10 Hz poll reads it like an input. Houdini has one interpolation per key, Blender one per Color Ramp and a handle type per curve point.
  - The Houdini bases are kept in `ramp_basis` and sent back while Blender's own setting still matches them: Linear and Constant with Vector, MonotoneCubic with Auto Clamped, the others with Auto. A Color Ramp takes the interpolation most keys use; between interpolations used as often, the one of the first key, so that a ramp gets the same one in every Blender session.
  - The curve widget's clipping rectangle covers every key.
- **Multiparms**: the count is an int input (`multiparm: true`, strict minimum 0) in the current folder. Each instance is a panel `<title> <n>` holding the instance parameters under their real names, with `#` replaced by the index, outer index first, and the start offset from `multiParmStartOffset`. Changing the count recooks, the new description changes the signature, and the inputs are rebuilt. The server sets values in passes (`set_parms`), since an instance parameter only exists once its count is set.
- **Nested panels**: folders travel as a list of labels, stored tab-separated. Blender 5.2 nests panels with `tree.interface.move_to_parent`, since `new_panel` has no parent argument. Inside a panel, Blender lists the inputs before the sub-panels.
- **Incremental rebuild**: `parameters.sync_interface` keeps an input whose parameter keeps its name and socket type, with its identifier, so keyframes and drivers on it survive a rebuild. Panels are reused by path, and the usage chain is made again.
- **Hidden and disabled**:
  - on the server, the states come from Houdini itself: `describe_parms` calls `node.updateParmStates()` once before it reads `isHidden()` and `isDisabled()` (see the hython pitfall under [Pitfalls](pitfalls.md#houdini)), so the states are those of the values just written and cooked (the order of `Server.cook`); when the call raises, every parameter is described visible and active.
  - Houdini hides or greys out everything a hidden or disabled folder holds, but leaves each parameter inside with its own state, so the walk passes the state of a folder down (`_folder_states`): a parameter is described hidden (disabled) when it is, or when a Simple or Collapsible folder or a multiparm that holds it is, nested folders and the instances of a multiparm included.
  - A Simple or Collapsible folder is read on its own folder-set parameter, whose state follows both its conditionals and its tab conditionals; a multiparm on its count. A tab is not read: the folder-set parameter of a set of tabs holds the tab conditions of its first tab only, or those of the whole set, and nothing tells which (see [Known limitations](pitfalls.md#known-limitations)).
  - Blender copies both states from every answer. On the Blender side, one function decides: `parameters.is_hidden(parm)`, hidden by Houdini and *Hide Like Houdini* on.
  - It is asked by the modifier panel (`parameters/layout.py`: a hidden parameter is not drawn, and a folder with nothing to show is not either) and, with the Houdini interface off, for `hide_in_modifier` (`sync_interface`, and `parameters.apply_houdini_interface` at each cook and when the preference changes).
  - A hidden parameter keeps its input, value, keyframes and drivers, and is still sent; `hidden` is not part of the signature, so a change rebuilds nothing. Changing `hide_in_modifier`, like any change of the node group's interface, marks input 1 to be read again once, and nothing is sent when it is unchanged.
  - `disabled` greys a parameter out in the panel (`UILayout.active` false): faded, not locked, since the state is that of the last cook and may be older than the values.
- **Code parameters**: see [Code parameters](#code-parameters).
- **Group fields**: string parameters with a `StringReplace` or `StringToggle` menu stay free text. Their menu items, the input groups as Houdini generates them but the empty ones, are sent as `suggestions` (`_describe_string` in `houdini/parms.py`), refreshed at every cook, and offered by a search popup next to the field (`houdini_bridge.pick_group`, through `parameters.group_suggestions`). A toggle field appends (`parameters.pick_group`).

## Code parameters

A string Houdini edits in a code editor (a wrangle's `snippet`, a Python SOP's `python`) is edited in Blender's Text Editor, in a window of its own, as Houdini's floating editor.

- **Found by its tags**:
  - Houdini marks such a template with the tags `editor` (`"1"`) and `editorlang` (`VEX` or `vex`, `python`, `opencl`, `hscript`, or none for multiline text, as `font.text`); some carry `editorlines` too (`8-30`), which is not used. `_describe_string` (`houdini/parms.py`) sends the language, lowercase, as `editor` (`text` when the tag names none).
  - Such a string sends no `suggestions`: the menu of a wrangle's snippet holds presets of code, not groups. Blender stores it in `HoudiniBridgeParm.editor` at every cook (`parameters.refresh_from_answer`), so a file saved before 1.0 gets its code block at its first cook, and the code presets it kept as suggestions are dropped. The input stays a String input, its value the code, sent and cooked as any string.
- **The code block** (`_code_block` in `ui/parameter_rows.py`):
  - the title, the *Edit* button (`code_editor.draw_edit`, the feature's own button) and a frame with the first `CODE_LINES` lines, tabs as spaces and long lines cut, then the count of the others, and under it the errors of the cook in red, whole and wrapped (`error_lines`): the status line shows only the start of each in a narrow editor, and a VEX error names the line and column of the code.
  - The one-line field is not drawn. With the Houdini interface off, Blender draws that field (a file saved so must show its parameters without the extension), and the block joins what the panel adds under the inputs (`beside_inputs`).
- **The mirror** (`features/code_editor.py`):
  - *Edit* (`houdini_bridge.edit_code`) makes a Text from the parameter, named `<node group> · <parameter><extension>`, the extension choosing the highlighting (`EXTENSIONS`: `.osl` for VEX, `.py` for Python, `.txt` otherwise), and opens it in a temporary window: `screen.userpref_show`, whose only area becomes a Text Editor with line numbers and highlighting.
  - The parameter stays the one reference. The Text is runtime data (`ID.is_runtime_data`): a save never writes it, while undo keeps it as any data. A second *Edit* on the same parameter while its window is open does nothing; a runtime Text of that name (one an undo or a redo brought back) is used again rather than doubled.
- **Following** (`code_editor.follow`, from a timer of `TICK` seconds registered when a mirror opens and gone when none is left, so nothing runs without an editor): a text that differs from the parameter and from what they last agreed on was typed, and is written into the input once typing has stopped for `DELAY` seconds; the 10 Hz poll of the cook engine sees the new value and cooks. A parameter that changed elsewhere (an undo of a parameter, a script) is copied into the text, the cursor kept. `save_pre` writes what was typed into the parameters (`flush`), so the file holds it.
- **Closing** (`code_editor.close`):
  - when its window is closed (what was typed is written first), when its modifier, node group or parameter is gone, when an undo takes the data back to before *Edit* (its Text is gone), on `load_pre`, and when the extension is disabled. The Text is removed and the window closed.
  - A file saved with an editor open keeps its window, the interface being saved, without the Text: `load_post` closes the temporary windows left holding only an empty Text Editor.
  - A Text removed after typing in it needs an undo step right after: Blender 5.2 crashes undoing a typing step of a Text that is gone (`txt_from_buf_for_undo`), so `close` pushes one (*Close Code Editor*), and *Edit* pushes its own, which the typing steps undo back to.
